# 从铁人三项到正式上线：状态机、线上故障与阿里云迁移

当猜曲、歌曲排序和老资历都能独立联机以后，我们开始制作铁人三项：三项固定顺序、每项三轮，共九轮累计积分。

真正困难的并不是把三个入口放在一起，而是让三个状态机共享一个房间、同一组玩家和一张总分表，并在项目切换时不留下旧状态。

## 九轮比赛的两套轮次编号

铁人三项需要同时记录：

- 总轮次 `overallRoundNumber`：1–9；
- 当前项目轮次 `stageRound`：每项重新从 1–3；
- 当前玩法 `activeMode`。

赛程固定为：

```text
总第 1–3 轮：猜曲
总第 4–6 轮：歌曲排序
总第 7–9 轮：谁是老资历
```

前端使用项目轮次显示“第 2/3 轮”，使用总轮次点亮赛程进度；服务端使用总轮次判断何时切换处理器和最终结算。

每轮开始时只初始化当前玩法所需字段，并重置玩家的本轮状态。总分、玩家身份、颜色和连接保持不变。曲目优先从整场尚未使用的歌曲中选择；曲库不足时允许合理重复，避免小曲库无法开局。

老资历阶段还加入难度递进：先选择发布时间相差 1–2 年的歌曲，最后一轮尽量压缩到 0–1 年。最终胜者会收到“恭喜 XXX 获得中V老资历大满贯！”的结算文案。

## 第一次线上教训：倒计时显示不等于权威时间

早期版本中，多个倒计时看起来会提前约三秒跳转。用户看到“剩余 3 秒”，页面却已经进入下一轮。

原因不是服务端真的少计时，而是客户端用自己的接收时刻显示剩余时间，没有正确消化服务端状态在网络上传输的延迟。显示值、状态广播和服务端推进由三套时刻共同影响。

修复后，每个房间投影都携带 `serverNow`。客户端收到消息时计算本地与服务器的偏移，并用校准后的时间显示倒计时。服务端仍然只认自己的 `endsAt`，客户端不会因为动画到零就擅自切换状态。

## 第二次教训：短暂的不完整状态足以让 React 白屏

铁人三项的排序环节曾在每轮结束时突然白屏，刷新后又恢复正常。这类现象通常说明服务端数据仍然存在，但前端某次渲染拿到了不适合当前组件的状态组合。

项目切换和轮间结算涉及 `phase`、`activeMode`、题目对象和下一轮时间。如果先改变玩法标识，再准备好对应题目，React 就可能按新玩法渲染旧数据；反过来也一样。

修复思路有两层：服务端尽量以一次对象更新提交完整状态，前端只在阶段和题目对象同时满足条件时渲染玩法组件。弹窗、答案和排行榜同样需要空值保护，不能假设 WebSocket 的每个快照都处于“理想页面状态”。

## 第三次教训：四人部分答对时的超时卡死

最隐蔽的问题出现在四人铁人三项猜曲：两人答对、两人未答，等待倒计时结束后没有弹出答案，刷新也可能继续卡住。双人测试往往因为两人都答对而提前结算，恰好绕开了超时路径。

规则本身没有问题。自动化测试直接把截止时间移到过去，服务端能够得到 `5、3、0、0` 并进入结算。真正需要加强的是运行环境中的计时可靠性：进程休眠、事件循环阻塞或部署恢复都有可能使预定计时器延迟。

最终采用两层兜底：

1. 客户端在校准时间超过截止 500 毫秒后，只发送一次 `sync`；
2. 服务端处理 `sync` 前先执行 `tick(Date.now())`，补做所有已经到期的状态转换。

这样计时器是主要触发器，任意在线玩家的同步或重连则是恢复触发器。客户端仍然不能决定结果，但房间不会因为一次漏唤醒永远停在过去。

## 为什么从 Cloudflare 迁移到阿里云

最初方案使用 Cloudflare Worker 与 Durable Object。它非常适合用单个强一致对象协调一个房间，并能用 Alarm 和休眠 WebSocket 降低空闲成本。

后续为了让服务部署、题库同步和运行环境更可控，我们保留协议与玩法处理器思路，将线上权威服务迁移到阿里云香港。新的部署结构是：

```text
B站 Toy / Cloudflare Pages
          │ HTTPS + WSS
          ▼
       Nginx
          ▼
Node.js RoomManager
          ▼
房间 JSON 持久化目录
```

systemd 负责开机启动和异常重启，Nginx 负责 HTTPS、WebSocket Upgrade 和证书入口。服务提供健康检查、题库版本、房间 REST API 与 WebSocket。

迁移能够保持前端改动很小，是因为房间协议从一开始就没有绑定到 Durable Object 的内部 API。前端只依赖 REST 路径、WebSocket 消息和协议版本。

## B站 Toy 中的 `Failed to fetch`

普通网页和服务器测试都正常，但 Toy 创建房间仍然报 `Failed to fetch`。最后发现 Toy 内容虽然从 B站入口打开，真正承载应用 iframe 的 Origin 是：

```text
https://www.bilibilitoy.com
```

服务端当时只允许 Pages 域名和 `https://www.bilibili.com`，因此 Toy 的 REST 预检和 WebSocket Upgrade 都收到 403。

把真实 iframe Origin 加入生产白名单后，我们分别验证：

- `GET /api/catalog` 返回 200；
- `OPTIONS /api/rooms` 返回 204；
- `Access-Control-Allow-Origin` 精确回传 Toy 域名；
- `wss://.../socket-test` 能完成双向回声；
- 四种玩法的公网房间流程全部通过。

这次问题提醒我们：嵌入式平台的访问入口域名、顶层页面域名和应用执行 Origin 可能完全不同。CORS 必须依据浏览器实际发送的 `Origin` 配置，不能凭地址栏猜测。

## Windows 打包脚本的最后一个坑

服务端发布包在 Windows 生成，上传后安装脚本报错：

```text
set: pipefail: invalid option name
```

真正的参数是 `pipefail\r`。Shell 脚本被 CRLF 换行污染，Linux 把行尾的回车当成参数内容。

仅在服务器执行一次 `sed` 能救急，却不能防止下次发生。我们最终修改发布脚本：先把文件复制到临时 staging 目录，对其中所有 `.sh` 统一转换为无 BOM 的 LF，再生成 `tar.gz`。这样既不依赖开发者本机 Git 换行设置，也不会修改工作区原文件。

## 上线的定义应该是“验证完成”

服务重启成功不等于上线完成。每次阿里云更新后，我们都会检查健康接口、题库版本、CORS、WebSocket 回声，并运行覆盖猜曲、老资历、排序和铁人三项的公网流程。

对于实时多人服务，部署动作只占最后阶段的一小部分。真正让版本可用的是：能发现旧状态、能从延迟中恢复、能解释跨域来源，并且能在真实公网入口上跑完一场游戏。
