# 从单机小游戏到多玩法联机架构

给一个已经能玩的单机项目加入多人联机，最危险的做法并不是“代码写得慢”，而是为了联机把原有玩法全部推倒重写。

「洛一把」已经有 React/Vite 前端、静态歌曲题库和本地游戏服务。我们的第一条原则因此很明确：**单机玩法继续按原来的方式运行，多人玩法作为一条独立路径加入。**

## 首版范围为什么很小

多人首版只做了这些能力：

- 创建 2–4 人房间；
- 房主选择目标人数、轮数和曲库；
- 生成六位房间码和邀请链接；
- 其他玩家输入昵称和房间码加入；
- 坐满后由房主开始；
- 完成所有轮次后显示排名。

没有大厅、自动匹配、账号、聊天、旁观、踢人和房间内重赛。这些功能并非没有价值，但它们会迅速把一个玩法项目变成社交平台项目。限制范围以后，我们才能先回答最重要的问题：同一道题如何同步、如何公平判分、掉线后如何回来。

## 保留单机服务，新增多人状态

原有的 `gameService`、歌曲搜索、字段标准化和反馈算法仍然保留。多人客户端复用它们完成输入联想和反馈展示，但不再拥有最终决定权。

新的多人系统分成三层：

```text
React 页面
  └─ WebSocket / REST 客户端
       └─ 通用房间会话 RoomSession
            └─ 具体玩法处理器
                 ├─ GuessSongMode
                 ├─ SeniorityMode
                 ├─ SortingMode
                 └─ TriathlonMode
```

通用房间层只关心成员、房主、连接、阶段、持久化和广播；玩法处理器只关心怎样出题、接收什么命令、什么时候结算，以及不同玩家能看到哪些状态。

每个处理器遵循相近的职责：

- `handleCommand`：处理经过身份校验的玩家命令；
- `tick`：根据服务端时间推进超时和下一轮；
- `addScheduleTimes`：告诉房间下一次应该何时醒来；
- `project`：按查看者身份生成可公开状态。

消息中保留 `mode` 和协议版本。这样客户端可以拒绝不兼容的旧协议，服务端也能在不改变房间外壳的情况下增加玩法。

## 从猜曲扩展到“谁是老资历”

多人猜曲稳定后，我们没有直接写铁人三项，而是先实现独立的老资历和歌曲排序。这一步非常重要：只有每个项目都能独立完成出题、同步、结算和投影，综合赛才只是“组合处理器”，而不是一团互相调用的页面逻辑。

多人老资历是一组同步二选一题：所有玩家看到同一对歌曲，发布时间在作答前隐藏。提交后选择锁定，但其他人的具体选择不会提前公开。全员作答或超时后，服务端统一揭晓发布时间、正确歌曲、玩家选择落点和所得分数。

为了兼顾知识和速度，正确玩家按服务端收到答案的顺序获得不同分数。玩家卡片上的歌姬代表色小方块，会在揭晓时落到各自选择的歌曲上。这既能表示选择分布，也复用了等待房间里的玩家视觉身份。

## 歌曲大排序为什么不能只在前端拖拽

歌曲排序要求每位玩家把五首歌按发布时间排成时间线。拖拽当然发生在本地，但玩家的完整排列属于私有答案，不能在每次移动时广播给对手。

服务端只公开“该玩家是否已经提交”和移动次数。提交后，再按照十组歌曲对的相对顺序计算正确数量。相比只检查五个绝对位置，这种评分方式能给“整体方向正确但有两首互换”的答案合理的部分分数。

同一轮还必须选择五个不同的发布时间，否则会出现无法定义先后的题目。选题器因此先按月份分桶，再从不同月份中抽取歌曲。

## 玩家颜色从座位默认值变成房间资源

初版将一至四号位固定成天依蓝、乐正绫红、言和绿和星尘紫。后来我们把颜色改成等待阶段可自主选择，并加入其他歌姬的代表色。

颜色不是装饰字段，而是一种房间内唯一资源：

- 服务端检查颜色是否合法；
- 同一房间不能使用相同色值；
- 掉线重连后保留原颜色；
- 游戏开始后锁定颜色；
- 所有玩法用同一颜色表示玩家。

这让后续界面不必反复写昵称。在排序提交状态、老资历选择落点、排行榜和彩带动画中，一个小色块就足以形成稳定识别。

## 轻量重构真正带来的收益

这次重构没有把单机玩法改造成联网玩法，而是把可复用的题库、搜索和判定能力留在公共服务中，把“谁决定状态”明确交给服务端。

最终我们得到的不只是三个多人页面，而是一套可继续容纳新玩法的结构。以后新增填字、抢答或团队模式时，首先要实现的是新的玩法处理器和隐私投影，而不是重新编写房间码、连接、成员和重连系统。

对于已有项目来说，这通常比追求一次性完美的“大一统架构”更可靠：先保护已经工作的部分，再为真正变化的部分建立清晰边界。
