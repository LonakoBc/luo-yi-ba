# 多人猜曲如何保证公平

单机猜曲只需要回答“玩家猜对了吗”，多人猜曲还必须回答另外三个问题：谁先猜对、倒计时到底以谁为准、其他玩家可以看到多少信息。

「洛一把」多人猜曲采用服务端权威模型。客户端负责输入、动画和倒计时显示，服务端负责选题、时间、提示、判分和阶段推进。

## 一轮比赛的完整规则

每轮开始时，2–4 名玩家同时获得同一道题，服务端记录：

- `startedAt`：开始时间；
- `endsAt`：三分钟后的截止时间；
- 当前答案；
- 已解锁提示等级；
- 每位玩家的猜测与本轮得分。

四人局正确顺序的积分依次为 `5、3、2、1`，少于四人时只使用前面的分数档。未猜出者得 0 分。全员提前猜出会立即结算，否则必须等待截止时间。

客户端提交只包含歌曲 ID。服务端从自己的题库查出歌曲，重新计算字段反馈，并以请求实际进入房间串行队列的顺序确定名次。即使两个请求几乎同时到达，也不会由客户端时间戳或网络往返时间自行决定先后。

截止边界也必须写清楚：

```text
receivedAt < endsAt   接受
receivedAt >= endsAt  拒绝
```

如果没有这一条，客户端显示 0 秒附近的答案就可能在不同机器上得到不同结果。

## 三段提示也是服务端状态

三分钟内依次解锁：

1. 开始 60 秒后：发布时间与歌姬；
2. 开始 120 秒后：STAFF；
3. 开始 150 秒后：歌词；
4. 开始 180 秒后：强制结算。

客户端可以根据服务器校准时间显示倒计时，但不能自行宣布提示已解锁。真正公开哪些字段由服务端投影决定。即使玩家修改本地时钟，也只能改变自己的动画，无法提前拿到后面的提示。

## 为什么对手不能收到完整猜测

多人猜曲的紧迫感来自“看到别人正在接近答案”，但如果把对手输入的曲名直接发过来，玩法就失去了意义。

因此同一个房间状态会按照查看者生成不同版本。

玩家本人可以收到：

- 自己选择的歌曲；
- 曲名、STAFF、发布时间、歌姬、声库、演出次数和标注等字段反馈；
- 每个字段的绿色、黄色或方向提示。

对手只能收到：

- 第几次猜测；
- 猜测发生时间；
- 是否完全正确；
- 本次公开反馈的颜色状态；
- 答对后获得的分数。

对手状态中不包含歌曲 ID、曲名文字和完整字段值。前端把它绘制成与真实表格相同的模糊单元格，所以玩家能看到某一列变绿或变黄，却无法读出对方填了什么。

这比把整行完全打码更有游戏性：信息足以制造压力，但不足以抄答案。

## 客户端为什么仍然复用单机服务

服务端权威并不意味着前端原有逻辑全部作废。歌曲联想搜索、用户输入标准化、表格组件和字段颜色仍然可以复用。

区别是：客户端搜索结果只是“准备提交的候选”，最终反馈必须来自服务端。这样既保留了单机版本成熟的输入体验，也避免客户端自行判分。

## 结算不是简单切换一个页面

每轮结束后，服务端公开完整答案。前端弹窗展示：

- 完整曲名；
- 发布时间；
- 演唱歌姬；
- STAFF；
- Bilibili 原视频与 VCPedia 页面；
- 单轮名次和得分；
- 下一轮倒计时。

玩家可以关闭弹窗查看上一轮的卡片状态，但倒计时仍按服务端时间继续。普通轮次等待十秒进入下一题；最后一轮不再等待，直接进入最终排名。

## 公平性的边界

这个系统防止的是正常游戏协议中的作弊：伪造时间、客户端自判正确、偷看对手提交和提前接收答案。由于歌曲题库本身是前端静态资源的一部分，它并不试图阻止玩家主动检查浏览器文件。

安全边界越诚实，架构就越清楚。对于轻量网页小游戏，服务端权威的核心价值不是构建反作弊系统，而是让所有正常玩家看到一致、可解释的比赛结果。
