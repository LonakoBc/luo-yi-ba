# 番外：B站 Toy 独立构建与多人游戏测试体系

「洛一把」同时发布在普通网页和 B站 Toy。我们没有复制一份 Toy 源码，而是为同一个项目增加独立构建目标。

这种方式的好处是修复只写一次，路由、资源和环境地址在构建阶段产生差异。与此同时，多人功能不能只靠“开几个浏览器试一遍”，它需要从规则函数一直验证到公网 WebSocket。

## 独立构建不等于复制项目

普通构建继续使用默认 Vite 配置，Toy 构建使用 `vite.toy.config.js`，主要差异包括：

- `base: './'`，确保资源使用相对路径；
- 使用 Hash 路由，让所有页面都留在一个 `index.html` 内；
- 注入 Toy JavaScript SDK；
- 写入阿里云多人 API 地址；
- 将 BGM 别名替换成 Toy 精简目录；
- 输出到独立的 `toy-dist`。

页面路由最终表现为：

```text
index.html#/multiplayer
index.html#/seniority/preset/all
```

刷新时服务器仍然只需要返回包内真实存在的 `index.html`，不会尝试寻找 `/multiplayer/index.html`。

## 为什么 Toy 包必须把资源平铺在根目录

第一版 ZIP 的 `index.html` 可以打开，但嵌套资源目录在一次更新后出现 404，页面因此白屏。

项目后来把所有发布文件平铺到 ZIP 根目录，并使用 ASCII 文件名：

```text
index.html
app-xxxx.js
asset-xxxx.css
asset-xxxx.png
asset-xxxx.mp3
```

Vite 的 `entryFileNames`、`chunkFileNames` 和 `assetFileNames` 都在 Toy 配置中单独指定。构建后校验器会拒绝任何子目录文件，避免“本地预览正常，平台更新丢失 assets 目录”的问题再次发生。

## 20MB 限制如何处理

完整网站有多首背景音乐，全部放进 Toy 包会明显超出建议大小。Toy 构建通过模块别名，只保留：

- 01《勾指起誓》；
- 02《普通DISCO》；
- 03《我的悲伤是水做的》；
- 04《一花依世界》；
- 05《世末歌者》。

歌曲题库和玩法代码保持完整，只精简全局 BGM。最终 ZIP 约 13.28MB，解压构建约 14.47MB。

发布前自动检查：

- 根目录存在 `index.html`；
- 文件后缀位于 Toy 白名单；
- 不存在嵌套文件；
- HTML 没有根绝对资源路径；
- 已注入 Toy SDK；
- JavaScript 包含正确的阿里云 API；
- 不再包含退役的 Cloudflare 服务地址；
- 总体积不超过 20MB 目标。

## Toy 发布为什么分成预览和审核两步

带包体的 `toy update` 首先上传一个预览版本，但不会直接提交审核。只有在浏览器验证预览后，再用完全相同的参数加确认选项提交。

我们的实际流程是：

1. 生成 `toy-dist`；
2. 构建校验；
3. 压缩根目录文件；
4. 上传仅预览版本；
5. 在预览中检查单机路由和多人入口；
6. 明确确认后提交审核；
7. 审核通过后自动替换线上版本。

这条流程尤其适合嵌入式平台，因为本地浏览器无法完全模拟平台 iframe、资源分发和 Origin。

## 第一层测试：纯规则函数

最底层测试不启动网络，专门验证不会因为 UI 变化而改变的规则：

- 2/3/4 人允许的轮数；
- `5、3、2、1` 抢答积分；
- 截止时间边界；
- 重复歌曲和答对后继续提交；
- 提示等级解锁时间；
- 老资历速度加分；
- 排序相对顺序得分；
- 同分并列与稳定排序；
- 曲库不足和日期不足。

规则函数越纯粹，越容易构造极端输入，也越容易判断失败究竟是规则错误还是网络错误。

## 第二层测试：房间集成

`RoomManager` 测试创建临时持久化目录和模拟 WebSocket，完整执行房间命令。它覆盖：

- 创建、加入和昵称冲突；
- 房主开始权限；
- 玩家颜色唯一；
- 猜曲隐私投影；
- 老资历选择隐藏与揭晓；
- 排序私有顺序；
- 九轮铁人三项累计积分；
- 刷新同步和超时追赶。

一次非常关键的回归测试专门构造四人铁人三项猜曲：前两人猜对，后两人保持未答，把截止时间移到过去，再通过第三名玩家的 `sync` 推动状态机。预期结果必须是结算阶段、完整答案公开、得分 `5、3、0、0`，并且没有服务端异常。

## 第三层测试：React 交互与响应式布局

组件测试关注用户实际能否完成操作：

- 创建与加入房间；
- 不同玩法配置；
- 等待房间和颜色选择；
- 对手模糊反馈；
- 答案弹窗和下一轮倒计时；
- 最终排名；
- 排序拖动与提交；
- 老资历选择锁定。

纯 DOM 测试无法发现所有排版问题，因此玩家截图仍然很重要。老资历移动端问题最后用 390×844 的普通手机视口和 390×2400 的 Toy 超长视口分别检查，确认卡片高度有上限、标题高度不为零，并且页面能够正常滚动。

## 第四层测试：公网冒烟验收

部署后测试直接访问生产地址，检查：

- `/health` 是否返回正确协议和题库版本；
- Toy Origin 的目录请求是否为 200；
- CORS 预检是否为 204；
- `Access-Control-Allow-Origin` 是否精确匹配；
- WSS 能否建立并完成回声；
- 四种模式能否创建房间并推进到预期阶段。

这一层无法替代单元测试，却能发现 DNS、证书、Nginx、Origin 白名单和 WebSocket Upgrade 等本地测试看不到的问题。

## 测试体系最重要的作用

多人游戏的错误往往只在特定人数、特定阶段和特定时间边界出现。手动测试很容易一直走“所有人迅速答对”的快乐路径，从而遗漏部分玩家未答、掉线或平台计时延迟。

好的测试体系不是追求一个漂亮的覆盖率数字，而是把每次真实事故变成以后不会再次悄悄出现的场景。规则测试解释结果，房间测试验证状态机，组件测试保护交互，公网测试确认部署环境——四层合起来，才接近玩家真正使用的系统。
